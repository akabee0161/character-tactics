# タイル関連ツール — 仕様

作成: 2026-09-19。**このファイルは作成時点のログ**。運用の最新は `README.md` と `CLAUDE.md` を見ること。

## 背景

アセット14点を作った時点で、同じ穴に2回落ちた。

1. **2x2 の城**（`castle_*` 4枚）を繋げて確認する手段がなく、`/tmp` にスクリプトを書いた
2. **川タイルの継ぎ目バグ**。1枚で見る限り完璧だったが縦に並べると境界に暗い横帯が出た。
   `validate.py` も `check_colors.py` も通過し、`_x8.png` の目視でも見つからない。
   確認のためまた `/tmp` にスクリプトを書いた

さらに、川の曲がり4種は互いのミラーなのに**独立した `.txt` を4枚**持っている。
HANDOFF 2.4 は「ミラー反転・オフセット・パレットサイクルはコード側の決定的変形で
生成すれば一貫性は原理的に100%」としているが、その変形の仕組みがない。

## ツール1: `tools/tilemap.py` — タイルを並べる

### 目的

`tile` 型は1枚の目視では検証が完了しない。並べた画像を作る手段を常設する。

### 動作

```sh
tools/tilemap.py --repeat river_v            # 1枚を 4x4 に敷く
tools/tilemap.py --repeat river_v --grid 3x3
tools/tilemap.py --layout map.txt            # 名前の並びから合成する
tools/tilemap.py                             # tile 型の全アセットを 3x3 で build/tiles/ に出す
```

レイアウトファイルは空白区切りのタイル名。`.` は空セル。

```
plain    plain     river_v  plain
plain    plain     bridge_h plain
plain    plain     river_ne river_h
```

出力は `build/tilemap/<name>.png`（等倍と拡大版）。

### 継ぎ目の機械チェック（実験）

「並べて初めて見える欠陥」が機械で拾えるかを試す。

**候補の判定式:** タイルをトーラスとみなし、巡回的な行差分
`d(y) = |{x : row_y[x] != row_(y+1 mod H)[x]}|` を全 y について求める。
列についても同様に `e(x)` を求める。継ぎ目をまたぐ位置（`d(H-2)`, `d(H-1)`, `d(0)`）の
最大値が、全体の中央値より一定以上大きければ警告する。

**根拠:** 壊れていた `river_v` では、行14→15 と 行0→1 で6セルが変化し、
それ以外の行はほぼ0だった。継ぎ目の周辺だけが突出する。

**採否は実測で決める。** 壊れた `river_v` を `tests/fixtures/` に再現して真陽性を測り、
現行12枚のタイルで偽陽性を測る。両者を分離できるしきい値が無ければ**この機能は入れない。**
`check_colors.py` で偽陽性の山を踏んだ反省を繰り返さない。

### 実測結果: 不採用

継ぎ目付近の突出（`near - median`）を測った。行と列の大きい方を示す。

| タイル | 突出 |
|---|---|
| **壊れた `river_v`** | **4.0** |
| `castle_se` / `castle_sw`（正常） | 12.0 |
| `castle_ne` / `castle_nw`（正常） | 11.0 |
| `river_ne` ほか曲がり4種（正常） | 8.0 |
| `bridge_h`（正常） | 0.5 |
| `plain` / `river_v` / `river_h`（正常） | 0.0 以下 |

**分離できない。** 壊れたタイルの 4.0 より、正常な城と曲がりの方が大きい。
城の分割タイルも曲がりも、そもそも自分自身と敷き詰めるものではないので、
端で大きく変化するのが正常である。

自分自身と敷き詰めるタイルに限れば 4.0 対 0.5 で分離できるが、そのためには
「このタイルは自己タイリングする」という宣言をヘッダに足す必要がある。
真陽性が1例しかない検査のために形式を広げる価値はないと判断した。
宣言を忘れなく書ける作業者なら、並べた画像を見ることも忘れない。

**よって継ぎ目の機械チェックは実装しない。** `tilemap.py` が全タイルの
3x3 画像を既定で出すので、目視は自動的に可能になる。
フィクスチャは `tests/fixtures/river_v_seam_bug.txt` に残し、
「安いチェックでは落ちない」ことをテストで固定した。

## ツール2: グリッドの決定的変形（HANDOFF 2.4）

### 目的

ミラーで作れるアセットを、独立したコピーとして持たない。

### 形式

本体を持たず、由来と変形だけを書いたグリッドファイルを認める。
あわせて、**コロンを含まない `#` 行をコメントとして認める**（フィクスチャに
経緯を書こうとして初めて、この形式にコメントが書けないことが分かった）。
コロンを含む `#` 行は従来どおり正しいヘッダでなければならない。
キーの打ち間違いが黙って無視されるのを防ぐため。

```
# from: river_ne.txt
# transform: mirror_x
```

- `from` は**同じディレクトリからの相対パス**
- `from` があるとき、`type` / `size` / `light` / `map` は由来元から継承する。
  書けば上書きできる
- 変形は1つだけ。連鎖が要るなら中間ファイルを作る

### 変形の種類

| 名前 | 意味 |
|---|---|
| `mirror_x` | 左右反転 |
| `mirror_y` | 上下反転 |
| `rotate_180` | 180度回転（`mirror_x` と `mirror_y` の合成） |
| `rotate_cw` | 時計回り90度。寸法が入れ替わる |
| `rotate_ccw` | 反時計回り90度。寸法が入れ替わる |

### 注意: 変形は光源を壊す

`# light: upper-left` を宣言していても、反転・回転すると光の向きは一緒に動く。
**陰影が変形軸について対称なアセットにしか使えない。** 川は水路の陰影が
左右対称なので問題ないが、顔グラや城には使えない。この制約は機械では検査しない。

### 既存ツールへの影響

解決は `gridfile.parse()` の中で行う。`Grid` を返す時点で変形済みの行を持つため、
`validate.py` / `render.py` / `check_colors.py` / `contact_sheet.py` / `tilemap.py` は
変更不要。

### 循環の防止

`from` を辿る深さに上限を設け、自己参照と循環を `GridError` にする。

## 適用

現行の `river_nw` / `river_se` / `river_sw` を派生ファイルに置き換える。

| ファイル | 由来 | 変形 |
|---|---|---|
| `river_nw.txt` | `river_ne.txt` | `mirror_x` |
| `river_se.txt` | `river_ne.txt` | `mirror_y` |
| `river_sw.txt` | `river_ne.txt` | `rotate_180` |

**移行の検証:** 置き換え後にレンダリングした PNG が、置き換え前の PNG と
ピクセル単位で一致すること。一致しなければ変形の実装が間違っている。

## やらないこと

- `offset`（オフセット変形）。HANDOFF 2.4 に挙がっているがアニメーション用であり、
  アニメーション機能自体がまだない
- パレットサイクル。同上
- 変形の連鎖記法
- 光源の整合性チェック
