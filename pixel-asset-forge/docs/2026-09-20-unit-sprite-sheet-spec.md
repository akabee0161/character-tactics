# `unit` 型 — タイル上を動くキャラクターのスプライトシート（仕様）

作成: 2026-09-20。**このファイルは作成時点のログ**。運用の最新は `README.md` と `CLAUDE.md` を見ること。

## 背景

[character-tactics](https://github.com/akabee0161/character-tactics) は、フィールド上のユニットを
**1ユニット1枚のスプライトシート**で描く実装をすでに持っている（`src/render/anim.ts`、
`src/engine/schema.ts`、`sheet-size.test.ts`）。並びの規約も固まっていて、PNG を上書きすれば
差し替わる状態にある。

いま入っている絵は `tools/gen-placeholder-sprites.mjs` が機械生成した仮のチビ体で、
本番の絵ではない。この仮絵を本リポジトリの資産で置き換えたい。

ただし本リポジトリに `unit` に相当する型は無い。`face`(32x32) / `item`(16x16) / `tile`(16x16) の
3つだけで、**型の一覧と未定義の型の解像度は「勝手に決めない」項目**である（`CLAUDE.md`）。

## この作業のゴール

**9体を量産することではない。1体（ロラン）を通して、仕組みの限界を測ること。**

依頼者の指定は次の3点。

1. フレーム規約は character-tactics の現行仕様を**固定の前提**とする（絵の都合で変えない）
2. 全シートの上書きを目標にしない。**まず1枚**作って、仕組み面の課題と限界を知る
3. ゲームに入れて動かすところまでやり、両リポジトリにコミットする

したがって成果物は「絵1枚」ではなく「**実測した限界のリスト**」である（7節）。

## 1. 固定された前提（character-tactics 側の規約）

読み取った実装は以下。これは動かさない。

| | |
|---|---|
| 並び | 1ユニット1枚。列 = コマ、行 = 12（3状態 × 4方向） |
| 行番号 | 状態index × 4 + 方向index。行 0-3 `idle` / 4-7 `walk` / 8-11 `attack`、各ブロック内は `down`, `up`, `left`, `right` |
| コマ | 正方形。`frame = 32` |
| コマ数 | `idle` 2 / `walk` 4 / `attack` 3。列数はシート全体で最大コマ数（4）に揃え、余りは透明のまま |
| 実寸 | 128 × 384 px |
| `down` | 手前向き（顔が見える） |
| 差し替え | `assets/images/roran-map.png` を上書きするだけ。コマ数を変えるなら JSON の数値も直す |

**`fps` は character-tactics 側の JSON が持つ**（`idle` 4 / `walk` 8 / `attack` 12）。
本リポジトリは持たない。

### 確認した事実（設計に効いたもの）

- **character-tactics にタイルマップは無い。** `src/render/draw.ts` にタイル描画は無く、
  ユニットはフィールド上に自由配置される。背景は敷き詰めたタイルではない。
  ただし依頼者の想定では、**将来このフィールドをタイルアセットに置き換える**。
- **`drawMapUnit` は `center - frame/2` で貼る。** ユニットの論理位置は
  **フレームの中心**であって足元ではない（3節に影響）。
- ゲーム内の `roran-face.png` は 5880色、4x4ブロックが崩れている。24x24 を Lanczos で
  128x128 に拡大したもので、**グリッド方式の資産ではない**。絵柄の基準には使えない。

## 2. `unit` 型を足す

4つ目の型として `unit` を追加する。

| | |
|---|---|
| 解像度 | 32x32（ゲーム側 `frame = 32` に合わせる） |
| 背景 | `bg: transparent` |
| 光源 | `# light: upper-left`（タイル65点と同じ） |
| 色 | `palette/master.json` を使う。色を足すときは描く前に `probe_colors.py` で草・道・床の色に対して測る |

### リファレンスは存在しない

`unit` 型に合格済みアセットは無い。**`face` の `knight.txt` は顔の描き方の基準であって、
タイル上を歩く全身キャラの基準ではない。** 仮スプライトシートも基準にならない。
つまり1体目は「絵柄に合わせる」作業ではなく「**この型の絵柄を最初に決める**」作業である。

既存資産から引き継ぐのは**マスターパレットと光源の2点だけ**に限定する。将来タイルの上に
乗せる前提があるため、この2点は揃えておく必要がある。

逆に `face` の流儀（全周に1pxの輪郭を回す、髪を4階調で塗る）は**持ち込まない**。
全身32pxでは顔が3〜4pxしかなく、同じ密度は物理的に入らない。
`tile` が `face` と別規約になったのと同じ構図である。

### `types/unit/SPEC.md` は今回書かない

`tile` は65点ある今も `SPEC.md` が無く、課題として残っている。1点しか無い段階で散文の仕様を
先に書くのは「絵柄は散文ではなく reference で揃える」という方針に反する。
**1体目が通ったら `types/unit/reference/` に昇格させ、それを基準にする。**

## 3. フレーム内の構図

今回いちばん効く決めごと。

| | |
|---|---|
| 足元 | **y = 30**（下端から2px上） |
| 左右 | 中央 |
| 背丈 | **24〜26px** |

将来16pxタイルを敷いたとき、背丈24pxは1.5タイル分になる。SFC世代の比率としては標準的な範囲。

### 受け入れる副作用: 論理位置が腰になる

ゲーム側は `center - 16` にフレームの左上を置くので、足元(y=30)は画面上では
**論理位置より14px下**に描かれる。つまり論理位置の高さはキャラの腰〜胸に来て、
**HPバー・リング・移動先の表示はすべてそこを基準にする。**

今回はゲーム側を変えない（現行規約に合わせる方針のため）。**「足元アンカーが無い」を
課題として記録する。** 将来16pxタイルを敷くと、キャラは論理位置のほぼ1タイル下に立って
見えることになるので、そのときに `sprites.ts` の1行を直す判断になる。

代替案は「足元をフレーム中央に置いて背丈16px」だが、盾持ちの騎士を16pxで描くことになり
情報量が足りないと判断した。

## 4. ファイル配置

既存ツールは変更不要である（確認済み: `gridfile` は `rglob("*.txt")` で階層を掘れる。
`# type:` は自由文字列で型ごとの解像度検査は無い。`render.py` は `build/unit/roran/` に出す）。

```
assets/unit/roran/*.txt              # 手描き18枚 + ミラー派生6枚
assets/unit/roran/roran.sheet.txt    # シート定義
types/unit/reference/                # 1体目が通ったら昇格。今回は空
```

## 5. シート定義と `tools/sheet.py`

### シート定義は `layouts/*.txt` と同じ流儀

タイルを並べる既存の仕組みと形式を揃える。新しい概念を増やさない。

```
# 12行 = 3状態 × 4方向。空白区切り、1行=シートの1行、`.` は透明のまま。
# 行 0-3 idle / 4-7 walk / 8-11 attack、各ブロック内は down, up, left, right

down_base   down_breathe  .            .
up_base     up_breathe    .            .
left_base   left_breathe  .            .
right_base  right_breathe .            .
down_base   down_walk_a   down_base    down_walk_b
（以下、walk の残り3方向と attack の4方向で計12行）
```

右向きは定義ファイルに特別な記法を作らない。`right_*.txt` を
`# from: left_*.txt` + `# transform: mirror_x` の派生ファイルとして置き、定義には普通の名前を書く。

### `tools/sheet.py` の仕事は3つ

1. 定義を読み、各グリッドを `gridfile.parse()` で読む（`# from:` の派生解決はその中で効くので追加実装なし）
2. **128 × 384 の透明PNGを出す**（これが納品物）
3. **目視用プレビューを x4 で出す。コマ境界線・足元ライン(y=30)・左右中心線を重ねる**

プレビューに線を重ねるのが効くと見ている。アニメで一番出る欠陥は
「コマ間で足元や体の中心が1pxずれて絵がガタつく」で、これは1コマの拡大画像を見ても分からない。
`tile` の「並べないと見えない」と同じ構図である。

`sheet.py` は各状態の実コマ数を印字する。**character-tactics の JSON は読まない**
（別リポジトリへの依存を作らない）。突き合わせは人がやる。

### 足元・中心の実測は助言に留める

表で出すが**非ゼロ終了はしない**。`attack` は踏み込みで足が動くのが正常なので厳格化できない。

このリポジトリは機械チェックの案を3回とも実測して撤回か下方修正にしている
（README「深いチェックを試して2回落としている」）。**実装したら全コマに掛けて偽陽性を数え、
数えた結果をそのまま README に書く。** 案の段階で「これは効く」とは書かない。

### テスト

`tools/` を触るので `tests/` に足す。定義のパース（行数12の検査、未定義名、`.` の扱い）と
組み立て後の寸法。比較用のグリッドは `tests/fixtures/` に固定する
（現役アートを参照させて `river_v` の作り直しでテストが落ちた件があるため）。

## 6. 描く枚数

| 方向 | idle | walk | attack |
|---|---|---|---|
| down / up / left | `base`, `breathe` | `walk_a`, `walk_b`（中間は `base` 流用） | `atk_wind`, `atk_hit`（戻りは `base` 流用） |
| right | 左向き6枚の `mirror_x` 派生（本体なし） | 〃 | 〃 |

3方向 × 6枚 = **18枚のフルグリッド**。

### なぜ差分の仕組みを先に作らないか

`# from:` の実装を読んで確認した。**派生ファイルは本体の行を持てず、5種の全体変形
（`mirror_x` / `mirror_y` / `rotate_180` / `rotate_cw` / `rotate_ccw`）しか掛けられない。
部分差分は作れない。** したがって歩行コマは `base` のコピーを数ピクセル直したフル本体になり、
これは「コピーで持たない」という原則と緊張する。

それでも**オーバーレイ機能や `shift_band` 変形を先に作ることはしない。**
どのピクセルが実際に変わるかは描く前には分からない。18枚を描いてから差分の実寸を測り、
その結果で「オーバーレイを足すか」「`shift_band` を足すか」「そのまま持つか」を決める。
機構を先に作らないのは、機械チェックで3回学んだことと同じ理屈である。

## 7. 検証手順と、測ること

### 検証は5段構え

上4つは既存のまま。5つ目が今回の本番。

1. `validate.py`（行長・未定義文字・パレット外）
2. `check_colors.py`（色を足したら。足す前に `probe_colors.py`）
3. 各コマの `_x8.png` 目視（1コマとして絵が成立しているか）
4. `sheet.py` のプレビュー目視（**コマ間で足元と中心がずれていないか**）
5. character-tactics に差し込んでブラウザで動かす（歩行・攻撃・向き変更・ドラッグプレビュー）

### 実測して README に書くこと

| 測ること | なぜ今わからないか |
|---|---|
| `mirror_x` の右向きが許容できるか | 光源が一緒に反転し、盾が反対の腕に移る。規約は「顔グラには使えない」。キャラで許せるかは見るまで不明 |
| 32px全身で4方向を描き分けられるか | 顔が3〜4pxしかない。前後の区別が付くかは描くまで不明 |
| 18枚の収束回数 | 既存の実測は `tile`(16px) と `face`(32px) の静止画だけ。アニメの収束回数は未知 |
| 足元・中心チェックの偽陽性数 | 案の段階では効くと言えない |
| 論理位置が腰であることの実害 | HPバーとリングが腰基準になる。画面で見るまで許容可否は判断できない |
| `base` と歩行コマの差分の実寸 | 差分の仕組みを足すべきかの判断材料（6節） |

## 9. この計画の弱点

正直に書いておく。

- **1体だけ本番絵にすると、残り8体の仮絵と画面上で並んで絵柄が混ざる。** ブランチに分けておけば
  main は汚れないが、目視の印象は「浮いた1体」になる
- **18枚が「手描きの32px限界」を超えている可能性がある。** README の実測では 32x32 の城が既に
  直接記述できず部品を組む形になった。結論が「案1では回らない」になる公算は現実にある。
  その場合でも7節のリストは残るので、パイロットとしては失敗ではないと考えている
- **`mirror_x` が却下されたら手描きは18枚から24枚に増える**（右向き6枚を描き起こす）
