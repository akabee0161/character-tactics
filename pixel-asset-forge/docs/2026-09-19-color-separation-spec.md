# 色分離チェック — 仕様

作成: 2026-09-19。**このファイルは作成時点のログ**。運用の最新は `README.md` と `CLAUDE.md` を見ること。

## 背景

アセット5点（顔グラ1・小物1・タイル5）を作り終えた時点で、`validate.py` が異常を
検出した回数は **0回** だった。収束に要した周回（宝箱5周・草原2周・城4周）は
すべて目視由来であり、「目視の前に機械チェックを挟めば往復回数が減る」という
HANDOFF 2.2 の前提は裏付けが取れていない。

原因の仮説は「チェックが浅い」こと。`validate.py` は行長・行数・未定義文字・
パレット外参照しか見ておらず、絵として成立しているかには触れていない。

[pixellint](https://github.com/Li-Mingshuang/pixellint) が同じ文字グリッド方式で
**隣接する色ペアの分離度**を定量判定しているため、その考え方を持ち込んで
効果を実測する。

## 目的

このチェックの目的は「往復回数を減らすこと」ではなく、**深い機械チェックが
実際に何を拾えるのかを数字で確定させること**。拾えないと分かることも成果とする。

## 判定規則

隣接（4近傍のうち右と下）する**異なる色**のペアをすべて抽出し、次で判定する。

1. **明度エッジがあれば無条件で合格。** L*（0〜100）について、
   絶対差 0.22（正規化後）以上、または明度比 1.7 以上。
   比を見るのは知覚が Weber の法則に従うため。暗部では小さい絶対差でも区別できる。
2. 明度エッジがない場合、**ΔE（CIE76, Lab）**で役割別に判定する。

| 役割 | hard failure | warning |
|---|---|---|
| `outline` と塗り | ΔE 24 未満 | ΔE 30 未満 |
| それ以外 | ΔE 6 未満 | ΔE 10 未満 |

`outline` は輪郭として存在する以上、溶けたら回復不能なので厳しくする。
それ以外は「文字どおり同じ色」の線を越えていれば作者の判断に任せる。

### しきい値は実測で校正した

pixellint の元の値は「それ以外」の warning が **ΔE 22**。この値を本リポジトリの
収束済みアセットに掛けると、**階調の隣り合いが全部警告になった**。

| ペア | ΔE |
|---|---|
| `stone_base` / `stone_hi` | 21.9 |
| `wood_base` / `wood_hi` | 20.3 |
| `skin_base` / `skin_shadow` | 19.4 |
| `hair_base` / `hair_shadow` | 13.9 |
| `grass_base` / `grass_hi` | 15.3 |

階調とはそもそも近い色を並べるものなので、これは偽陽性である。pixellint 自身が
「**厳しすぎるチェッカーは拾う以上のコストを払う**」と実例13件付きで記録しており、
その罠に即座に踏んだ形になる。

収束済みアセットが無警告になるまで下げ、**ΔE 10** を採用した。

## 適用範囲と除外

- **塗られたセルのみ**を対象とする。背景セル（`.`）は対象外。したがって
  グラデーション背景に乗ったスプライトは、背景との分離を検査しない
- ΔE は CIE76（Lab のユークリッド距離）。CIEDE2000 は使わない。しきい値自体が
  粗いので精度が釣り合わない

## 実装しなかったもの

**孤立ピクセル検査**（周囲すべてと大きく異なる1pxを検出する）を試作したが**削除した。**
草原の初版で `grass_dark` の孤立点が虫に見えた件を拾う意図だったが、
**斜めの輪郭を全部検出した。** 斜めの輪郭ピクセルは定義上4近傍すべてと色が違うため、
ドット絵で最も正常な構造を欠陥として報告してしまう。概念から誤っていた。

## 位置づけ

`validate.py` とは分離する。

| | 責務 | 異常時 |
|---|---|---|
| `validate.py` | グリッドとして成立しているか（構造） | 常に非ゼロ終了 |
| `check_colors.py` | 絵として区別がつくか（助言） | hard failure のときだけ非ゼロ終了 |

目視の代替ではなく補助。pixellint は「**見ることのできないモデル**」を前提に
アサーションを視覚の代替として設計しているが、本リポジトリは Claude が
`_x8.png` を Read できる前提で、目視が主・機械チェックが従である。

## 実測結果

### 偽陽性（収束済み7グリッド）

校正前 6件が警告、校正後 **0件**。

### 真陽性

| 対象 | 結果 |
|---|---|
| 重複パレット色を隣接させた対照 | **検出**（ΔE 0.0） |
| 城2周目の「消えた目地」を再現 | **検出できず** |
| `types/face/reference/knight.txt` | **検出**（`outline` / `pupil` が ΔE 0.0） |

### 分かったこと

**このチェックが拾えるのは「パレット上は別名だが実質同じ色」が隣接している場合だけ。**

城の「目地が消えた」「塔が壁と分離していない」は、*同じ色*が隣り合っていた
ケースであり、色ペアが発生しないので原理的に検出できない。「胸壁が黒い塊に見える」
は構図の問題で、色の問題ではない。

つまり **目視で見つけた11件のうち、このチェックで拾えたものは0件**。
一方で、**目視で5点分見逃していた欠陥を1件拾った**（knight の瞳孔）。

機械チェックと目視は代替関係ではなく相補関係にある、というのが実測の結論。
機械は「同じ色に別の名前が付いている」を見つけ、目は構図を見つける。

## 既知の未解決

`types/face/reference/knight.txt` は `check_colors.py` で hard failure のまま残す。
`outline` と `pupil` に同じ `#1a1228` が割り当たっており、瞳孔が目の輪郭に同化している。
HANDOFF 4節は「目が 白目／虹彩／瞳孔 の3要素」を到達点に挙げているが、実際には
3要素になっていない。

修正には `pupil` の色を決める必要があり、これは HANDOFF 3節で未確定とされている
「マスターパレットの具体的な色」に当たるため、**このタスクでは触らない。**

同様の重複が `hair_hi` と `cloth_hi`（ともに `#7a8fd0`）にもあるが、
この2色は現時点でどのアセットでも隣接していない。
