# ドット絵アセット生成リポジトリ — 引き継ぎ

## このドキュメントの使い方

Claude Code にこのファイルを読ませて、リポジトリ構築から継続する。
検討の経緯と、**確定していること／していないこと**の区別を含む。
未確定の項目を勝手に確定させないこと。

---

## 1. 目的

Claude Code でゲームアセット（ドット絵）を効率的に生成する。
対象は Ankardo（子供向けゲーム、web-novel-engine）。

課題は「生成できるか」ではなく**品質と、1アセットあたりの往復回数**。
Claude Code でドット絵を描くこと自体は既に実績がある。

---

## 2. 確定していること

### 2.1 生成方式

**テキストグリッドを正とし、スクリプトで PNG にレンダリングする。**

PNG を直接生成しない。1文字＝1ピクセルの文字グリッドをソースとして git 管理し、
`render.py` が PNG に変換する。

利点:
- git の差分が「1行＝1ピクセル行」になり、修正箇所が追える
- 再生成が決定的
- パレットの差し替えが一括で効く

### 2.2 検証ループ

Claude Code 内で以下が1セッションで閉じる。これが設計の軸。

```
グリッド記述 → レンダリング → 機械チェック → Claude が PNG を目視 → 修正
```

**目視の前に機械チェックを挟む。** パレット外の色、行の長さ、寸法、
アセットあたりの使用色数。安価で大半の不整合を拾える。

### 2.3 パレット

- プロジェクト全体で**マスターパレット**を持ち、色の統一はここで担保
- マスターの色数に強い制約は置かない（256色でも運用上の問題はない）
- 気にすべきは**各アセットが実際に何色使うか**の方

### 2.4 アニメーション

T2I や LLM に複数フレームを描かせない。
ミラー反転・オフセット・パレットサイクル・数フレームの差分は
**コード側の決定的変形**で生成すれば一貫性は原理的に100%。

### 2.5 アセット種別による手段の分離

| 種別 | 手段 | 理由 |
|---|---|---|
| 小物・UI・タイル | コード生成 | 形が単純で指定量が少ない。**主戦場** |
| 顔グラフィック | コード生成（検証済み） | 32×32 で実用水準に到達した |

顔グラについては、ドット絵にこだわらず通常の CG 絵を使う選択肢も残っている。

### 2.6 絵柄を言葉で指定するのは低精度

「ファイアーエムブレム風」のような指定では、階調・目の構造・髪の流れが伝わらない。
**型ごとに合格済みアセットを reference として置き、それを読ませて揃える**方が精度が出る。
散文の SPEC はパレット・寸法・構成要素など機械的な規約に限定する。

---

## 3. 未確定のこと

勝手に決めないこと。必要なら依頼者に確認する。

- **目指す絵柄** — SFC世代相当の作り込みで満足、という以上の指定はない。
  レトロ機の制約（16色縛り等）を再現する意図は**ない**
- **解像度** — 32×32 は検証で使った数字。型ごとに決める
- **アセットあたりの色数上限** — 未定。実測で決める
- **マスターパレットの具体的な色** — 未定
- **型の一覧** — 顔グラ以外は未着手

---

## 4. 実績のある成果物

`seed/face32.py` に、32×32 の顔グラフィックを生成する動作済みコードがある。
16色使用。これがリポジトリ設計の出発点。

到達した品質:
- 肌に4段の階調、頬と顎下に影
- 目が 白目／虹彩／瞳孔 の3要素
- 髪に4段の階調、左上光源で方向が一貫
- 背景にグラデーション

残る不足（次の改善対象）:
- 髪がヘルメット状で毛束・流れがない
- 眉と上まつげが分離せず黒い横棒になっている
- 顔の輪郭が長方形で頭蓋の丸みがない
- 首が太く肩との境界が不明瞭

**注意:** `face32.py` はパレット・グリッド・検証・描画が1ファイルに同居している。
リポジトリ化の際に分解すること（後述）。

## 5. リポジトリ骨組み

```
pixel-assets/
├── CLAUDE.md                    # 常時読まれる規約（短く保つ）
├── palette/
│   └── master.json              # 色名 → RGB
├── types/
│   ├── face/
│   │   ├── SPEC.md              # 寸法・構成要素・機械規約
│   │   └── reference/           # 合格済みアセット＝お手本
│   │       ├── knight.txt
│   │       └── knight.png
│   └── item/
│       ├── SPEC.md
│       └── reference/
├── assets/                      # 生成物（グリッドが正）
│   ├── face/
│   │   └── <name>.txt
│   └── item/
│       └── <name>.txt
├── tools/
│   ├── render.py                # txt → png
│   ├── validate.py              # 機械チェック
│   └── contact_sheet.py         # 全アセットを1枚に並べる
└── build/                       # png 出力（.gitignore）
```

### 5.1 グリッドファイル形式

```
# type: face
# size: 32x32
# light: upper-left
# map: o=outline e=hair_hi f=hair_base g=hair_sh h=hair_dark a=skin_hi ...
................................
.............oooooo.............
...........ofeeeeeffo...........
（以下32行）
```

- `map` の色名は `palette/master.json` のキーを参照する
- `.` は背景（透過または型ごとの背景処理）
- 1行＝32文字。`validate.py` が長さを検証する

### 5.2 各ツールの責務

| ツール | 責務 |
|---|---|
| `render.py` | `assets/**/*.txt` → `build/**/*.png`。等倍と拡大版の両方を出力 |
| `validate.py` | 行長・行数・未定義文字・パレット外参照・使用色数を検査。異常時は非ゼロ終了 |
| `contact_sheet.py` | 全アセットを1枚に並べる。型をまたいだ絵柄のズレを目視で発見するため |

`render.py` は拡大版（8倍程度、最近傍）を必ず出すこと。
等倍 PNG は Claude が目視する際に小さすぎる。

### 5.3 CLAUDE.md に書くこと

短く保つ。以下程度。

- グリッドが正、PNG は生成物であること
- 新規アセット生成時は必ず `types/<type>/SPEC.md` と `reference/` を先に読むこと
- 目視の前に `validate.py` を通すこと
- 完成後 `contact_sheet.py` を更新すること

## 6. 作業手順（想定される運用）

```
依頼者: 「item型で、木製の宝箱を1つ」
  ↓
Claude Code: types/item/SPEC.md と reference/ を読む
  ↓  assets/item/chest.txt を書く
  ↓  validate.py → render.py
  ↓  build/item/chest_x8.png を Read して目視
  ↓  問題があれば自分で修正、なければ提出
  ↓
依頼者: 「蓋の金具が目立ちすぎる」
  ↓
Claude Code: 該当行を特定して修正 → 再レンダリング
```

## 7. 最初にやること

**型定義を先に作り込まない。**
現時点で合格例は顔グラ1枚のみ。小物は1点も作っていない。

推奨する順序:

1. `tools/` 3本と `palette/master.json` を作る（`face32.py` を分解して流用）
2. `types/face/` に今回の顔グラを reference として登録
3. **`item` 型で小物を1点作り、何周で収束するか実測する**
4. 3の結果を見てから `types/item/SPEC.md` を書く

3が最優先。小物こそが主戦場であり、まだ1点も検証していない。
SPEC は実物ができてから書く。
