# 戦闘 UI ユーザビリティ改善 設計書

作成日: 2026-08-26

## 1. 背景

縦切り 1 本が動く状態になった後、実際にプレイして次の 4 点が使いにくいと判明した。いずれも「何が起きているか分からない」「思った通りに動かない」であり、ゲームバランスではなく操作の可読性の問題である。

1. 襲撃開始前の配置フェーズで、今どのキャラを選択しているのか分からない
2. 戦闘中、キャラを選択して移動先を選ぶ操作がやりにくい
3. 移動先を選んでも、そこへまっすぐ進まない
4. 移動先を選んだ後、誰がどこへ向かっているのか分かりにくい

攻撃モーションの分かりにくさも認識しているが、将来的にスプライト画像へ置き換える前提のため、本設計のスコープ外とする。

## 2. 目的

本作の主目的は「ユニット1体1体にキャラクター性を持たせること」（`2026-08-17-character-tactics-design.md` 第1章）である。誰がどこで何をしているかが読めないことは、この主目的と直接競合する。本設計は**盤面の可読性と操作の予測可能性**だけを対象とし、ゲームルール（戦闘計算・交戦条件・スキル効果）は一切変更しない。

## 3. 現状の原因

コードを読んで特定した原因は以下の通り。

### 3.1 配置時に選択が見えない

`main.ts` の `placement` ケースは `dragging` のみ設定し、`selected` は `null` のままになる。選択ハイライトの描画（`draw.ts` の `drawAllies`）と下部ポートレートの反転（`screens.ts` の `drawBottomBar`）はどちらも `selected` を見るため、配置フェーズでは常に「誰も選ばれていない」表示になる。

またポートレートのタップ選択は `battle` フェーズにしか実装されていない。

### 3.2 入力系統が二重になっている

移動命令の発行経路が 2 つある。

- `pointerdown` で、選択中キャラがいて地面をタップしたとき即座に `move` コマンドを積む
- `pointerup` で、ドラッグ中だったキャラに `move` コマンドを積む

前者があるため、選択解除の手段がない状態で地面に触れると必ず移動命令になる。誤タップがすべて移動になり、意図しない再配置が起きる。

### 3.3 経路が階段状になり、狙った点で止まらない

`field.ts` の `computeFlowField` は 4 近傍の BFS である。`flowDirection` は隣接セルの中心へ向かう単位ベクトルを返すため、斜め方向の移動が構造的に存在せず、必ず軸に沿った階段状の経路になる。

さらに `flowDirection` はゴールセルに入った時点（`curDist === 0`）で `null` を返す。ユニットが状態として持っているのはフローフィールドだけで、タップされた座標そのものを保持していないため、**タップ点ではなくそのセルに入った瞬間に停止する**。セルは 32px なので、最大でセル 1 個ぶんずれる。

### 3.4 移動先が残らない

移動マーカーは `main.ts` のモジュール変数 `moveMarker` 1 個だけで、しかも 400ms で消える。キャラごとの目的地という概念が状態にないため、4 人ぶんを同時に表示できない。

## 4. 設計

### 4.1 目的地を状態として持つ（`goalPos`）

`AllyUnit` に `goalPos: Vec2 | null` を追加する。移動命令を受けたときに `goalField` と一緒に設定し、到達・交戦・退場・スキルによる移動打ち切りで `null` に戻す。

これが 3.3 の「狙った点で止まらない」と 3.4 の「誰がどこへ向かうか分からない」の共通の土台になる。描画側は `goalPos` を読むだけでよく、UI 層にマーカー用の状態を持たせる必要がなくなる。

`goalField` は残す。障害物を回り込む経路計算には引き続き必要で、`goalPos` はその最終目標点を表す。

### 4.2 経路: 8 近傍 + 直線ショートカット（A+B）

2 つの変更を組み合わせる。

**A: フローフィールドの 8 近傍化**

`computeFlowField` を 4 近傍 BFS から 8 近傍ダイクストラに変える。コストは整数スケールで直交 10・斜め 14（`√2 ≒ 1.4`）とし、`FlowField.dist` の型（`Int32Array`）は変えずに済ませる。

斜め移動はコーナーカットを禁止する。すなわち `(dx, dy)` の斜め遷移は `(cx+dx, cy)` と `(cx, cy+dy)` の両方が歩行可能なときのみ許可する。これがないと壁の角をすり抜ける。

グリッドは最大でも 30×14 = 420 セルなので、優先度キューは実装しない。未確定セルから最小コストを線形探索する素朴なダイクストラで十分速く、コード量も少ない。フィールドの再計算は移動命令の発行時のみ発生する。

**B: 直線ショートカット**

`hasLineOfSight(grid, from, to)` を追加する。2 点を結ぶ線分上を細かくサンプリングし、すべて歩行可能セルなら `true` を返す。

移動処理では、ゴールまで視線が通っていれば**フローフィールドを無視して `goalPos` へ直行**し、遮られている間だけフローフィールドに従う。開けた地形ではセル中心を経由しない完全な直線になり、障害物の裏へ回り込む間だけ 8 近傍の経路をたどって、視線が通った瞬間に直線へ切り替わる。

**到達判定**

残り距離が今フレームの移動量以下になったら、`pos` を `goalPos` に一致させて `goalPos` と `goalField` を `null` にする。これで「タップした点で止まる」が成立し、セル中心付近での往復も起きない。

**採用しなかった案: A\* + string pulling**

経路としては最もきれいだが、`goalField` の構造を捨てることになる。敵は全体で `enemyField` を共有しており（`BattleState.enemyField`）、味方だけ別方式にすると移動の実装が二本立てになる。得られる見た目の差に対して負担が大きく、採らない。

**既存テストへの影響**

`FlowField.dist` の単位がセル数からスケール整数コストへ変わるため、値を直接検査している以下を更新する必要がある。

- `src/core/field.test.ts` の `computeFlowField` / `flowDirection` のケース
- `src/core/state.test.ts` の `enemyField.dist` の検査

`src/content/stages/stages.test.ts` は `> 0` の検査のみなので影響しない。

### 4.3 入力の一本化

移動命令の発行を `pointerup` に統一し、`pointerdown` では選択とドラッグ開始のみ行う。

ドラッグ距離のしきい値（論理座標で 12px）を導入し、

- しきい値未満で離した = **タップ**。味方の上なら選択、地面なら選択中キャラへの移動命令
- しきい値以上動いて離した = **ドラッグ**。掴んだキャラへの移動命令（配置フェーズなら再配置）

選択解除の手段を用意する。選択中のキャラをもう一度タップすると解除する。地面タップは移動命令に使うため、空白タップでの解除は割り当てられない。

味方のヒット判定半径を 24 から 32 へ広げる（`hit.ts` の `pickAlly` の既定値）。ユニットの描画半径は 11 で、指での操作には 24 は小さい。

### 4.4 配置フェーズの選択表示

`selected` を `placement` と `waveCleared` でも設定する。既存のハイライト描画とポートレート反転がそのまま効くため、描画側の変更は不要。

ポートレートのタップ選択を全フェーズで有効にする。配置フェーズではこちらが主導線になる。

`placeAlly` は歩行不可セルだと黙って `return` するため、置けなかったときに完全な無反応になる。戻り値を `boolean` に変え、失敗したことを UI が知れるようにする。ドラッグ中のゴースト表示（4.5）を配置不可の位置では赤くすることで、離す前に分かるようにする。

### 4.5 目的地とドラッグの可視化

`drawMoveMarker`（単一・400ms）を廃止し、`goalPos` を読む常時表示に置き換える。

- 選択中のキャラ: 現在地から目的地への線と、キャラ色のマーカー
- 非選択のキャラ: マーカーのみ、細く小さく
- 交戦中のキャラ: マーカーを半透明にする。交戦中は移動しないが `goalField` は残り、交戦が解けたら再開するため、消すと嘘になる

ドラッグ中は、指の位置にキャラ色の半透明ゴーストと、現在地からの線を描く。配置フェーズで歩行不可セルの上にいるときはゴーストを赤くする。

## 5. スコープ外

- 攻撃モーション・被弾表現（将来スプライトへ置き換える前提）
- 敵の経路。敵は `enemyField` を共有しており、8 近傍化の恩恵は自動的に受けるが、直線ショートカットは適用しない（敵が壁沿いに素直に来るほうが読みやすいため）
- ゲームバランス、スキル効果、交戦条件
- ステージデータ、キャラクターデータ

## 6. 制約（既存設計から引き継ぐもの）

- ゲーム内に表示する日本語は全文ひらがな・カタカナ。漢字を使わない
- `src/core/**` と `src/content/**` は `window` / `document` / `HTMLCanvasElement` / `localStorage` を参照しない
- 論理解像度 960×540 固定。ボタンの当たり判定は論理座標で最小 64×64
- コミットは Conventional Commits 形式
