# ユニットの絵をゲームの描画で確かめるコマンド（unit-view）の設計

2026-11-28

## 目的と理由

- ドット絵のユニットを作るたびに、pixel-asset-forge の決まり（`pixel-asset-forge/CLAUDE.md`「`unit` 型も1枚の目視では終わらない。… ゲームで動かすこと」）で、ゲーム内の確認が求められる。今は、セーブを localStorage に入れてタイトル → ステージ選び → 出撃と画面操作を数十手進める必要があり、動きのページ（`tools/anim-page.py`）で代えるか、省いてきた（PR #74 では依頼者が「ゲーム内の確認はやらない」と決めた）
- **この仕組みを使うのは依頼者ではなく、作業するエージェントの自動の確認**（依頼者 2026-11-28）。目視の画面ではなく、1 つのコマンドで合否が出ることを目指す
- 残る作業（PR 6 のノエル ally08・ピコ ally11、主人公 4 人とガルムの見直し、敵の見直し）で使う

## 目標

1. ブラウザを使わずに確かめられることは Vitest で確かめる（`npm test` に入る）
2. 描いて初めて分かることだけを、開発用の別ページとゲームの描画関数で描き、画素を照らし合わせる。`npm run unit-view` 1 つで、開発サーバの起動 → Chromium で開く → 照らし合わせ → 結果の表示と終了コード、まで済ませる
3. 本番の配信物（`out/play/character-tactics/`）に、このページとその JavaScript が入らない

## やらないこと

- **スマホの倍率（0.796 倍など）で線が消えるかの確認。** 依頼者が「縮小を理由に絵を変えない。直すのはゲーム側」と決めている（`pixel-asset-forge/ISSUES.md`「ゲームが整数倍でない倍率で描く」、2026-09-25）ので、落ちても絵を直す理由にならない。ページは論理座標の 1px = 画面の 1px で描く
- 地形・敵・技の演出との重なりの確認（戦闘から直接始める案 B は取らなかった。下の「案」）
- 目視用の操作（向きやコマを選ぶ UI）。ページは全部を一度に並べるだけ
- ゲーム本体（`index.html`・`src/main.ts`）の `?debug` の変更
- `pixel-asset-forge/` のコピーの変更（forge の決まりの書き換えは、この作業に入れない）

## 作るもの

### A. シートの中身のテスト（Vitest）

新しいテストファイル（例 `src/engine/sheet-frames.test.ts`）。`sheet-size.test.ts` と同じく `assets/units`・`assets/enemies` のシートを持つ定義を読み、PNG を `node:zlib` で展開して画素を読む（依存を増やさない。対応する PNG の形式は、今の書き出し（`pixel-asset-forge/tools/export.py`）が出す形式だけでよく、それ以外は分かる言葉で失敗させる）。

行ごと（状態 × 方向）に確かめること:

1. JSON のその状態のコマ数より左の列は、どのコマにも不透明な画素がある
2. コマ数から右の列（最大のコマ数に満たない状態の余り）は、全部透明
3. 足元の行（y = `frame - FOOT_INSET`。32px で y=30、48px で y=46。`bodyCenter` と同じ定数 `FOOT_INSET` を import して使う）より下の行は、全部透明

**足元の行に画素があるか（足が線に着いているか）は確かめない**（私の判断）。飛ぶユニット（ピコ ally11）や歩きの足を上げたコマで成り立たないうえ、forge の `unit_check.py`・`sheet.py` の赤線が絵の側で見ているため。

同じシートを複数の定義が指すとき（敵の見た目の違い）は、シートのファイルごとに 1 回だけ確かめる。

今のアセットで流して落ちるものがあれば、テストの条件を緩めず、どのシートのどのコマかを依頼者に報告する（依頼者が承認済みの絵なので、直すかどうかは依頼者が決める）。

### B. 描画の切り出し（`src/render/draw.ts`）

`drawUnits` のループの中の、絵と「絵に付いて回る印」（弓を通しにくい印・旗・選択の輪・踏ん張りの輪・狙い撃ちの輪・強化の印・HP バー）を描く部分を、1 体ぶんを描く関数に切り出して export する。`drawUnits` はそれを呼ぶだけにし、戦闘の見た目は変えない。ページはこの関数を呼ぶので、ゲームと同じコードで描かれる。

- 引数は、絵の中心 `p`・`radius`・定義・コマ（`AnimFrame`）・味方か・HP の割合・印の有無など。`Unit` と `BattleState` を丸ごと渡さなくて済む形にする（ページで偽の戦闘を組まなくてよいように）。細かい形は実装者が決める
- 「体だけ」「印だけ」を描き分けられること（暗いステージの `'bodies'` / `'marks'` と同じ分け方）。ページはこれで、体だけの画素と、印を足した後の画素を別々に取る
- 飛ぶユニットの足元の影（`drawUnits` の楕円）と、跳ぶ技・飛行の持ち上げの計算は `drawUnits` に残す。影は絵ではなく地面の印なので、切り出す関数に入れない（私の判断。入れると、影がコマの下端の行に掛かり、D の照らし合わせで飛ぶユニットが必ず落ちる）。持ち上げた後の中心 `p` を引数で渡す
- 描画コードなのでユニットテストは書かない（CLAUDE.md）。戦闘の見た目が変わっていないことは、切り出しの前後で同じ画面を撮り、画素が一致することで確かめる（下の「確かめ方」5）

### C. 開発用のページ

- `unit-view.html`（リポジトリの直下。`index.html` の隣）と、その入口 `src/dev/unit-view.ts`
- `vite build` は `build.rollupOptions.input` を指定しない限り `index.html` しか入れないので、本番の配信物に入らない。実装後に `npm run build` の `out/` に `unit-view` の名の付くファイルが無いことを確かめる
- ゲームと同じ `loadRegistry`・`imageUrls`・`makeImageCache` を使う。画像は全部読み終わるのを待ってから描く（ゲームは待たないが、ページは待つ。読み終わる前に描くと丸のプレースホルダが写る）
- キャンバスは論理座標 1px = CSS 1px = 画面 1px（`devicePixelRatio` は 1 に固定。スクリプトが `Emulation.setDeviceMetricsOverride` で 1 にする）。`computeViewport` の拡大は使わない
- 背景は、どのパレットにも無い単色（例 `#ff00ff`）。ここに地形は描かない
- 並べ方: シートのファイルごとに 1 区画。区画の中は 12 行（状態 × 方向、`frameOf` と同じ順）× 最大のコマ数の升。升の大きさは、絵と印（旗は右上に、HP バーは上にはみ出す）が隣の升に掛からない大きさ。並べ方の計算は純関数にして（例 `src/dev/unit-view-layout.ts`）Vitest で確かめる（升どうしが重ならない、全部がキャンバスに収まる）
- 区画ごとに、そのシートを使う定義を 1 つ選んで描く（味方の定義が指すシートは味方として＝旗あり、敵のシートは敵として。ally06・ally08 のシートは味方と `-foe` が共有するので味方として描く）。飛行（`flying: true`）の定義は、ゲームと同じく絵を `FLYING_LIFT`（5px、`draw.ts` から export する）だけ持ち上げて描く。影は描かない（B）
- 描く印は、その定義が持つものだけ（私の判断）: 味方なら旗、全員に HP バー（満タン）、`bowDamageCap` を持つ定義なら弓の印。選択・踏ん張り・狙い撃ち・強化の輪と印は、戦闘の状態でしか出ないので描かない
- 区画の左上に、シートの名前と定義の ID を文字で書く（撮った画面を人が読むため）。文字は升の外に置き、判定に入れない

### D. 照らし合わせ（ページの中で行う）

升ごとに:

1. **絵の一致（合否に使う）**: 体だけを描いた画素を、シートの該当のコマ（`frameOf` を使わず、行 = 状態 × 4 + 方向・列 = コマ番号を、このページの側で独立に数える）と比べる。期待する置き場所も、`bodyCenter` を使わず「足元の行がその升の足元の点に来る」位置として独立に計算する（飛行の定義は、そこから `FLYING_LIFT` だけ上）。比べる範囲は、期待する置き場所のコマの正方形と、その周り 1px（絵が升の中でずれてはみ出した場合を拾うため）。不透明な画素は色が一致し、透明な画素は背景色のまま、を全部の画素で見る。1 画素でも違えば落ちる
2. **印のかぶり（報告だけ）**: 印を足した後の画素と体だけの画素を比べ、絵の不透明な画素のうち印で塗り替わった数を数える。今の作りでは旗がコマの右上に掛かるので 0 にならない升がある。**かぶりを不具合とするかは依頼者が決めていないので、合否に使わず数だけ出す**（私の判断）

比べる関数は、画素の配列を受け取る純関数にし（例 `src/dev/unit-view-compare.ts`）、Vitest で確かめる（一致・1 画素ずれ・色違い・透明の扱い）。

結果は `window` の 1 つの値（例 `window.__unitView`）に置く: 完了したか、升ごとの合否と違った画素の数、印のかぶりの数。

### E. 判定のスクリプトと `npm run unit-view`

- `tools/unit-view.ts`（`vite-node` で動かす。`balance` と同じ形）
- vite の開発サーバを、スクリプトの中から `createServer` で起こす（ポートは引数で。既定は空いている番号を vite に選ばせる）
- Chromium を `--headless=new --no-sandbox --disable-gpu --remote-debugging-port=<port>` で起こす。実行ファイルは環境変数 `CHROME`（無ければ分かる言葉で止める。パスをスクリプトに書かない）、ポートは環境変数 `CDP_PORT`（既定 9333）。CDP は Node の組み込みの `WebSocket` で話す（依存を増やさない）
- `window.__unitView` が完了になるまで待ち（上限の時間を置く）、画面を撮って PNG で保存する（保存先は引数。既定はリポジトリの外に出さず、git 管理外の `out/unit-view/`。`out/` は `.gitignore` にある。`npm run build` は `emptyOutDir` で `out/play/character-tactics/` だけを消すので、`out/unit-view/` は残る）
- 表示: シートごとに 1 行（合否・違った升の数・印のかぶりの最大）。落ちた升は、シート・状態・方向・コマ番号・違った画素の数を出す
- 終了コード: 全部一致で 0、1 升でも違えば 1、ページが開けない・時間切れ・Chromium が起きないは 2
- 終わったら（失敗しても）Chromium と開発サーバを止める
- メモリ: スクリプトはメモリの制限を掛けない。README に、`free -m` で空きを見ること、`systemd-run --user --scope -p MemoryMax=…` を付けて起こす例を書く

## 確かめ方（実装の終わりに）

1. `npm test`（約 4 分、背景で流す）
2. `npm run build` が通り、`out/` に unit-view のファイルが無い
3. `npm run unit-view` が今のアセットで 0 で終わる（落ちたら、A と同じく依頼者に報告）
4. **わざと壊して落ちることを確かめる**: 一時的に描画の側の足元の高さ（`FOOT_INSET` の使い方）を 1 ずらす、行の並びを入れ替える、の 2 つで 1 になる。確かめたら戻す（コミットしない）
5. B の切り出しの前後で、戦闘の画面の画素が一致する。撮り方（私の判断）: 一度きりの確認なので、撮影用の入口はリポジトリに残さない。作業ツリーの外（スクラッチ）に、`createBattleState` を固定の種で作って `drawBattle` に渡すだけの一時ページを置き、切り出しの前のコミットと後のコミットで同じように撮って比べる。ステージは明るいもの 1 つと暗いもの 1 つ。暗いステージの膜は実時刻（`performance.now()`）で揺れるので、CDP の `Page.addScriptToEvaluateOnNewDocument` で `performance.now` を定数に差し替えてから撮る
