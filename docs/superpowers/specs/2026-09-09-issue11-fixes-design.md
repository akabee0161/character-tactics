## 1. 目的

issue #11 に挙がった12項目の修正要望に対応する。内容は大きく4系統に分かれる。

正典（README.md / CLAUDE.md）の書き換えをスコープに含める。

## 3. 座標とサイズの土台（項目4）

### 3.1 確認した原因

`index.html` の `#game` に `max-width: 540px` が付いている。一方 `src/main.ts` の `resize()` は
インライン style で幅と高さを入れる。インライン指定は `max-width` を上書きできないため、
論理解像度 540×945 に対する拡大率が 1 を超える環境（`window.innerHeight` が 945px を超える場合）で、
高さだけが伸びて幅が 540px で頭打ちになる。

この状態では次の2つが起きる。

- canvas の backing store（`540 × scale × dpr` 幅）が 540px の CSS ボックスへ押し込まれ、横に潰れて描かれる
- 入力側は `getBoundingClientRect()` の実寸（潰れた後の 540×1080 など）から拡大率を逆算するため、
  描画が使った拡大率と食い違う。1920×1080 のウィンドウでは描画 scale 1.14 / 入力 scale 1.00 となり、
  さらに入力側だけ縦 67.5px のオフセットが入る

「ウィンドウを小さくすると問題なく遊べた」という報告は、拡大率が 1 以下になると `max-width` に
当たらなくなることと一致する。

### 3.2 方針

**サイズ決定の責務を JS 一本に統一する。** CSS とJS が同じ寸法を別々に決めて食い違う構造自体を壊す。

- `index.html` の `#game` から `max-width` / `max-height` / `aspect-ratio` / `width` を外す。
  canvas に残す CSS は `display: block` / `touch-action: none` / `image-rendering: pixelated` のみ
- canvas を `<div id="stage">` で包む。この div が safe-area の内側を占める箱になり、
  safe-area の扱いは CSS 側に残す
- JS は `window.innerWidth` / `innerHeight` を直接見るのをやめ、`#stage` の実寸を測って canvas を合わせる
- `window` の `resize` イベント購読をやめ、`#stage` への `ResizeObserver` に替える。
  ブラウザのズーム操作による `devicePixelRatio` の変化も拾えるようにする

### 3.3 インターフェース

`src/render/viewport.ts` に純関数を足す。DOM に触らないのでユニットテストできる。

```ts
export type CanvasFit = { cssW: number; cssH: number; pixelW: number; pixelH: number };
export function fitCanvas(boxW: number, boxH: number, dpr: number): CanvasFit;
```

`main.ts` 側の手順は次の通り。

1. `#stage` の `getBoundingClientRect()` を測る
2. `fitCanvas` で CSS 寸法と backing store 寸法を決め、canvas に入れる
3. **入れた後にもう一度 canvas の `getBoundingClientRect()` を測り、その実寸から backing store を確定する**

手順3は保険である。将来 CSS が何らかの制約を効かせても、描画と入力が同じ実寸を見ているかぎり
クリック位置はずれない。ずれる代わりにレターボックスが出るだけになる。

## 4. 下パネルの再編（項目3・5・6・7・12）

### 4.1 現状

下パネル（論理 y 786〜945）は2つの要素で構成されている。

- ポートレート4枠（y 858, 高さ 80）— タップで選択／選択解除

### 4.2 新しい構成

**上段 `MESSAGE_BAR`（y 788〜852）**

| フェーズ | 表示 |
|---|---|
| 配置 | 「はじめる」ボタン |
| 戦闘 | セリフ欄 |

セリフ欄は左に 48px の顔、右に本文2行（フォント 18px、行高 22px）を置く。顔で話者が分かるので

この配置により、戦闘中のセリフが盤面を隠さなくなる（項目6・7）。

**下段 ポートレート4枠（y 858〜938）**

タップの意味を「選択／選択解除」から「必殺技の発動」へ変える（項目5）。

- タップで必殺技を発動し、同時にそのキャラを選択する
- クールダウン中、必殺技を持たない、退場済みのいずれかなら選択だけ行う
- `needsDest` の技（かけぬける）は既存の `pendingSkill` 機構を流用し、次のマップタップで方向を決める
- 発動できる状態のときは枠を明るい縁にする。残り時間は既存のクールダウンゲージで読む
- レベルを枠の右上に出す（項目12）。名前の右は `roleBadgeIn` のロールバッジと干渉するため

選択の解除はマップ上のキャラの再タップだけになる。下パネルからは解除できなくなる。

### 4.3 削除するもの

`src/ui/skillbutton.ts` と `src/ui/skillbutton.test.ts` を削除する。このモジュールは
「押せない理由を文字で見せる」ためのラベル（「なかまを えらぶ」「わざめい あと○びょう」）を

無くなるため、理由の文字列が不要になる。押せるかどうかはポートレートの縁とゲージで示す。

下パネル領域（`y >= BOTTOM_PANEL_Y`）のタップは、どの矩形にも当たらなくてもマップ操作へ
落とさない。現在は矩形を外れると `beginMapPointer` へ流れている。

### 4.4 「はじめる」が暗く見える問題（項目3）

`src/ui/screens.ts` の `button()` は有効時 `#2c4a63`、無効時 `#2a2f35` を塗る。どちらも暗い
紺〜灰で、並べない限り区別がつかない。

`button()` に primary 配色（塗り `#ffd479`、文字 `#1a1a1a`）を足し、主要導線のボタンに適用する。
対象は「はじめる」「はじめから」「つぎへ」「もういちど」。無効時は現状の暗い灰のままにして、
有効と無効が色で明確に分かれるようにする。`#ffd479` は既にゴール旗・クールダウンゲージ・
配置範囲で使っているアクセント色で、新しい色を増やさない。

## 5. 吹き出しの撤去とセリフの一本化（項目6）

### 5.1 削除するもの

セリフを下パネルへ移すので、頭上の吹き出しに付随する機構を丸ごと削除できる。

- `src/ui/layout.ts` の `bubbleRectAt` / `bubbleLines` / `BUBBLE_*` 定数
- `src/ui/screens.ts` の `drawBubble`
- `src/main.ts` の `bubbleAt`
- `src/ui/input.ts` の `PointerStart.bubbleUid` と `MapGesture` の `dismissBubble`
- 対応するテスト（`bubbles.test.ts`、`layout.test.ts` と `input.test.ts` の吹き出し関連）

「吹き出しをタップして消す」「吹き出しの上から始めたドラッグはタップ扱いにしない」という
2つの特殊扱いが不要になるため、ポインター処理が単純になる。

### 5.2 残すもの

`src/ui/bubbles.ts` を `src/ui/speech.ts` に改名し、状態を単純化する。

```ts
export type Speech = { uid: string; defId: string; text: string; ttl: number };
export type SpeechState = { current: Speech | null };
```

現在は uid をキーにした `Map` で複数の吹き出しを同時に出している。セリフ欄は1件しか出せないので
`current` 1件に変える。新しい発話は上書きする。

**複数の発話が同じ tick に発生した場合は、`pickDialogue` が返す配列の先頭だけを採用する。**
`pickDialogue` は優先順位（rival → first → skill → levelup → pinch → win → retire）で並べて返すので、
末尾で上書きすると優先度の低いセリフが勝ってしまう。

表示時間は現状の 3.0 秒を変えない。

## 6. 配置フェーズ（項目2）

### 6.1 スキーマ変更

ステージ定義の `placementZone: { pos: Vec2 }[]` を次に置き換える。

```ts
placement: {
  /** この y 以上（画面で下）なら配置できる */
  minY: number;
  /** ステージ開始時の4人の初期位置 */
  starts: Vec2[];
}
```

検証（`src/engine/schema.ts`）は次を要求する。

- `minY` は 0 以上、マップ高さ未満
- `starts` は1要素以上、各要素は歩けるマスであり `y >= minY`

既存3ステージの `placementZone` の4座標はそのまま `starts` へ移す。`minY` は現在の配置円
（中心 y 592・656、半径 64）が覆っていた範囲の上端に合わせて **528** とする。

### 6.2 判定の一本化

`src/core/state.ts` に判定を1本置き、配置の実行とドラッグプレビューの両方が通る形にする。

```ts
export function canPlaceAt(stage: StageDef, grid: Grid, pos: Vec2): boolean;
```

`placeUnit` の円判定（`PLACEMENT_RADIUS` を使った距離判定）をこれに置き換え、`PLACEMENT_RADIUS` は
廃止する。`src/main.ts` のドラッグプレビューの `blocked` 判定も同じ関数を通す。現在プレビューは
歩けるかどうかしか見ていないため、配置領域の外でも赤くならない。これが直る。

### 6.3 描画

配置円の黄色い破線をやめ、`minY` の高さに横一本の黄色い破線を引き、その下を薄く塗る
（`rgba(255, 212, 121, 0.12)`）。文言は「黄色い線より下に 仲間を おこう」とする。

## 7. 敵（項目8・9・10）

### 7.1 移動速度（項目8）

`assets/enemies/*.json` の `speed` を25%下げる。

| 敵 | 現在 | 変更後 |
|---|---|---|
| ならずもの | 45 | 34 |
| たてもち | 35 | 26 |
| ガルム | 55 | 41 |

味方はガウが 100、他の3人が 60。変更後は味方（60）と敵（26〜41）に明確な差がつき、
「撃ちながら下がる」という選択肢が成立する。

### 7.2 時間湧き（項目9）

ステージ定義に湧き口を足す。

```ts
spawners?: {
  defId: string;
  pos: Vec2;
  /** 戦闘開始から最初の湧きまでの秒数 */
  firstAfter: number;
  /** 2体目以降の間隔（秒） */
  every: number;
  /** この湧き口から湧く総数の上限 */
  total: number;
}[]
```

- 検証: `pos` は歩けるマス、`firstAfter` は 0 以上、`every` と `total` は 1 以上
- 湧いた敵の AI は `aggressive` 固定とする。要望が「こちらに向かってくる敵」なので、
  索敵範囲や視線を持たせない
- 総数上限を必須にする。上限がないと持久戦で詰む。勝利条件は `reach`（本拠地到達）なので、
  上限付きの湧きは「急がせる圧力」として働き、詰みを作らない

実装は純ロジックと状態更新を分ける。

```ts
// src/core/spawns.ts
export function dueSpawns(
  spawners: Spawner[], counts: number[], time: number,
): { index: number; spawner: Spawner }[];
```

`dueSpawns` は湧き口1つにつき1回の呼び出しで最大1体を返す。`counts[index]` が `total` に
達している湧き口は返さない。n 体目が出る時刻は `firstAfter + every × (n - 1)` とする。

`BattleState` に `spawnCounts: number[]`（湧き口ごとの累計）を持たせ、`step()` の先頭で
`dueSpawns` を呼んで敵を足す。敵 Unit の生成は現在 `createBattleState` 内にインラインで
書かれているので、`makeEnemyUnit(reg, uid, defId, pos, ai)` として切り出し、初期配置と
時間湧きの両方が同じ経路を通るようにする。uid は既存の `state.nextEnemyUid` を使う。

湧いた瞬間が分かるよう、湧き口に出現エフェクトを出す（`src/render/effects.ts` に1バリアント追加）。
セリフ欄は味方の発話用なので使わない。

配置は **ステージ2とステージ3に1か所ずつ**。ステージ1は導入なので湧きを置かない。

湧いた敵にも `xpReward` があるため、§8 の経験値源としても働く。

### 7.3 索敵範囲の非表示（項目10）

`src/render/draw.ts` の `drawSightRanges` と `src/render/objectives-view.ts` の `sightCircles` を
削除し、代わりに追跡状態のサインを返す関数を置く。

```ts
export type AlertMark = { pos: Vec2 };
/** 追跡に入っている敵の位置。範囲は見せず、気づかれたことだけを伝える */
export function alertMarks(units: Unit[]): AlertMark[];
```

`ai.mode === 'chase'` の敵を返し、`draw.ts` が頭上に赤い「！」を描く。状態を別に持たないので、
追跡が切れれば自動的に消える。

`objectives-view.ts` に残っている「索敵範囲の表示は装飾ではない」というコメントは、今回の判断
（範囲が見えると緊張感が削がれる。気づかれたことは「！」で伝える）に書き換える。

## 8. 成長（項目11・12）

### 8.1 方針

レベルアップの**頻度**と、1レベルあたりの**強化量**を分けて調整する。頻度を上げるだけだと
上限のレベルに短時間で到達して強さが壊れるため、上限を上げ、1レベルの上昇を緩やかにする。

調整値はすべて `assets/growth.json` に置き、コードに直書きしない。プレイして甘すぎた場合に
JSON だけで戻せるようにする。

```json
{
  "maxLevel": 12,
  "xpPerLevel": 12,
  "hpPerLevel": 1,
  "levelsPerPower": 3,
  "hitXp": 1,
  "healXp": 1,
  "assistRatio": 0.5,
  "clearXp": 10
}
```

### 8.2 ステータスの式

`src/core/state.ts` の `statsForLevel` を変える。`steps = max(0, level - 1)`。

| | 現在 | 変更後 |
|---|---|---|
| 最大HP | `def.maxHp + steps × 3` | `def.maxHp + steps × hpPerLevel`（= 1） |
| 攻撃力 | `def.power + steps × 1` | `def.power + floor(steps ÷ levelsPerPower)`（3レベルごとに +1） |

ロランを例にした結果。

| | 現在 Lv5（上限） | 変更後 Lv5 | 変更後 Lv12（上限） |
|---|---|---|---|
| 最大HP | 42 | 34 | 41 |
| 攻撃力 | 10 | 7 | 9 |

上限での強さは現状とほぼ同じまま、そこへ到達するまでのレベルアップ回数が4回から11回に増える。

攻撃力を整数で刻むため `floor` を使う。`computeDamage` は整数前提で組まれているので、
小数の攻撃力を入れない。

### 8.3 経験値の源

現在は「とどめを刺した1人が `xpReward` を受け取る」のみ。これを4種に増やす。

| 源 | 受け取る側 | 量 |
|---|---|---|
| 命中 | 攻撃した側 | `hitXp`（1） |
| 回復 | 回復した側 | `healXp`（1） |
| 撃破 | とどめを刺した側 | `xpReward` 全額 |
| 撃破 | その敵にダメージを与えた他の味方 | `xpReward × assistRatio`（半額） |
| ステージクリア | 退場していない味方全員 | `clearXp`（10） |

経験値が入るのは `side === 'player'` のユニットだけとする。敵が味方に命中させても敵は育たない。

アシスト配分のために `Unit` に `damagedBy: string[]`（その敵に当てた味方の uid、重複なし）を足し、
`applyDamage` で記録する。既存の `lastHitBy` はとどめ判定に使い続ける。アシストの配分先からは
とどめを刺した本人を除く（二重取りを避ける）。

命中と回復の経験値は、`applyDamage` / `useSkill` の中ではなく `sim.step` で `hit` / `heal`
イベントを見て配る。イベント発行はすでにあるので、経験値の加算箇所を `growth.ts` に集約できる。

`xpReward` も引き上げる。

| 敵 | 現在 | 変更後 |
|---|---|---|
| ならずもの | 5 | 8 |
| たてもち | 8 | 12 |
| ガルム | 20 | 30 |

### 8.4 必要経験値

`xpToNext(level) = level × xpPerLevel` は式を変えず、`xpPerLevel` を 30 から 12 へ下げる。
`src/core/progress.ts` の定数 `XP_PER_LEVEL` と `MAX_LEVEL` を廃止し、`assets/growth.json`
から読んだ値を引数で渡す形にする。

| | 現在（上限 Lv5） | 変更後（上限 Lv12） |
|---|---|---|
| Lv2 まで | 30 | 12 |
| Lv5 まで（累計） | 360 | 120 |
| 上限まで（累計） | 360 | 792 |

新しい経験値源だと1ステージで30〜50程度入る見込みで、3ステージ通してだいたい Lv5 前後になる。
上限の Lv12 は1周では届かず、周回の伸びしろとして残る。**この見積りは計算によるもので、
実際のプレイでは確認していない。** 初回の目視確認時に実測し、必要なら `assets/growth.json` を
調整する。

### 8.5 既存セーブとの互換

`MAX_LEVEL` は `src/save/save.ts` の検証では使われておらず、`progress.ts` の `applyXp` でのみ
参照されている。上限を上げても保存済みの Lv1〜5 はそのまま有効に読める。

### 8.6 レベル表示（項目12）

ポートレート枠の右上にレベルを出す（§4.2）。リザルト画面は既にレベルを表示している。

### 8.7 レベルアップのセリフ

`src/core/dialogue.ts` は `levelUp` イベントごとに `levelup:<defId>` のセリフを出す。レベルアップが
増えればセリフ欄の占有も増える。§8.4 の見積りでは1ステージあたり1〜2回のため、今回は間引きの
仕組みを入れない。目視確認で多すぎた場合に対処する。

## 9. 表記の漢字化（項目1）

### 9.1 範囲

画面に出る文字すべてを漢字仮名交じりにする。ルビは付けない。常用漢字を中心に、低学年でも
読める語を選ぶ。

対象。

- `src/ui/screens.ts` — タイトル、ステージ選択、配置、リザルト、敗北、ロードエラー
- `src/render/draw.ts` — 表示文字列
- `src/main.ts` — 読み込み失敗時のメッセージ
- `assets/lines/common.json` — 全行
- `assets/stages/*.json` — `name`、`intro`、`outro`
- `assets/skills.json` — `label`
- `assets/titles.json` — `label`
- `assets/units/*.json`、`assets/enemies/*.json` — `name`、`role`

### 9.2 正典の更新

- `CLAUDE.md` — 「画面に出す文字は総ひらがな（子ども向けの表記）」の方針を削除し、
  新方針（漢字仮名交じり、ルビなし）に差し替える
- `README.md` — 操作説明に出てくる UI 文言（「なかまを えらぶ」など）を新しい文字列に更新する。
  §6 のスキーマ変更（`placement`、`spawners`）と §8 の `assets/growth.json` も
  「コンテンツの足しかた」へ反映する

### 9.3 注意点

`src/ui/layout.ts` の幅見積り `measure = (t) => t.length * FONT_PX` は全角前提である。
「Lv3」のような半角混在の文字列では幅を過大に見積もる。セリフ欄の折り返し幅の計算は
この前提を踏まえて組む。

漢字化により同じ内容の文字数は減るので、会話ウィンドウ（3行・26px）の収まりは悪化しない。

## 12. 既知のリスク

- **§8 の経験値設計は計算による見積りで、実測していない。** 4種の経験値源を同時に入れるため、
  実際には想定より緩くなる可能性がある。調整値を `assets/growth.json` に集約するのはこのため
- **選択の解除手段が減る。** §4.2 により、ポートレートからの選択解除ができなくなり、
  マップ上のキャラの再タップだけになる
- **`placement` へのスキーマ変更は後方互換ではない。** 既存3ステージの JSON を同時に直す必要がある。
  ステージ JSON はリポジトリ内にしかないため、外部への影響はない
